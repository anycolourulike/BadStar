# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BadStar is a mobile action game targeting Android (`com.anycolouryoulike.BadStar`, target SDK 28).

- **Unity version:** `2022.3.62f3` (revision `96770f904ca7`), from `ProjectSettings/ProjectVersion.txt`.
- **Render pipeline:** URP 14 (`com.unity.render-pipelines.universal` 14.0.12). The active pipeline asset is `Assets/_Renderer/BadStarURP.asset` (renderer: `BadStarURP_Renderer.asset`), assigned in Graphics settings and the highest quality level. Use URP/Shader Graph shaders. Built-in pipeline materials render pink. Legacy Post-processing v2 (`com.unity.postprocessing` 3.4.0) is also installed, and its profiles sit in `Assets/PostProcessing Profiles/`, but URP uses its own Volume system.
- **Input:** legacy Input Manager (`Input.GetTouch`). The new Input System package is not installed.

There is no `.asmdef` for `_Scripts`, so all game code compiles into `Assembly-CSharp`. The root `.csproj`/`.sln` files are generated by Unity, so don't edit them by hand.

## Assets/ structure

Folders starting with `_` are the project's own content. Everything else is imported third-party or Unity-generated content. Don't edit it unless asked.

**Project content**
- `_Scripts/`: all game C# (see Architecture). It also holds data assets next to the code: `ProgressionSO/` (stat progression), `QuestSO/` (quest assets) and `MapLocations/`.
- `_Scenes/`: `Menu/` holds Preloader, Menu and Loading. The two levels are `CrashSite.unity` (formerly F3) and `Mine.unity`, each with a same-named folder for its lighting/NavMesh data. `HopperCrashSite/` holds the crash-site prefabs. Each level's NavMesh comes from a `LevelNavMesh` NavMeshSurface on an unrotated root object (a rotated surface tilts every agent).
- `_Prefabs/`: `PlayerCore/` (player rig and HUD, which `LevelManager` looks up as `/PlayerCore/HUD/Dialogue`), `Characters/`, `Weapons/`, `PickUps/`, `Ships/`, `Hopper/`, `Wayfarer/`, `Cameras/`, `Enviroment/`, `GameObjs/` and `_Graphics/`.
- `_Animations/`: controllers and clips for `Rambler` (player), `Timbertoes`, `AI Humanoid`, `PauseMenu` and `AvatarMasks`.
- `_UI/`: UI prefabs (`UI`, `Stats Canvas`, `Frame`) and `Inventory/`. `_Images/` holds UI sprites (death and game-over screens, loading images).
- `_Renderer/`: URP pipeline and renderer assets. `_Shaders/`: the Dissolve Shader Graph (used by `DissolveObject`). `_Materials/`: skybox and Rambler materials.
- `_AssetPacks/`: purchased art, VFX and SFX packs (FORGE3D, PolygonSciFiSpace, JMO, footsteps, gun SFX, …). Treat these as third-party.
- `AddressableAssetsData/`: Addressables groups and settings. A new level scene must be added to a group here, as well as wired into `LevelManager`.
- `SceneRefs.cs` (loose in `Assets/`): the per-scene reference holder that `LevelManager` finds on load.

**Third-party / generated**
- `Feel/`, `Photon/`, `LeanTween/`, `GoogleMobileAds/`, `ExternalDependencyManager/`, `TextMesh Pro/`
- VFX and art packs: `EffectCore/`, `ExplosiveLLC/`, `Hovl Studio/`, `PolygonParticleFX/`, `Grunge UI Kit/`, `PostProcessing Profiles/`
- `Plugins/`: native platform plugins (`Android/`, `iOS/`, `tvOS/`)
- Unity-managed: `Resources/`, `StreamingAssets/`, `Editor Default Resources/`, `Samples/`, `Settings/` and `UniversalRenderPipelineGlobalSettings.asset`
- Probably leftovers: `Scenes/`, `Assets/Assets/`, `Unity/`, `GameDev.tv Assets/`, `Standard Assets/`, `DefaultNetworkPrefabs.asset` (from the Netcode template) and `Penthouse.fbx`, which appears both loose and in `_Scripts/`

## Architecture

Namespaces are `Rambler.*`: Combat, Control, Core, Dialogue, Inventories, Quests, Saving, SceneManagement, Stats, UI, Attributes. A few files use different names: `GameDevTV.Utils`, `GameDevTV.Core.UI.Tooltips`, and the typos `Rambler.Comabt` and `Rambleer.Control`. Fix those namespaces only when asked, because scene and prefab references are keyed by class and namespace. Much of the core (Saving, Stats, Dialogue, Quests, Inventories, ActionScheduler, LazyValue) is adapted from the GameDevTV RPG course framework.

### Scene flow and `LevelManager`
- Build-settings scenes: `Preloader` → `Menu` (via Addressables) → `Loading` → gameplay. Most gameplay levels are **Addressable scenes**, not build-index scenes.
- `Managers/LevelManager.cs` is a `DontDestroyOnLoad` singleton (`LevelManager.Instance`) and the central hub. An integer `sceneRef` selects the level `AssetReference` in `FindAssetPath()` (0 Menu, 2 Crash Site, 3 Mine; 1 was the old Intro and falls back to the Crash Site, anything else to the Menu) and the ambient music in `AmbientMusic()`. To add a level, update both switches and add an `AssetReference` field.
- To change level, set `LevelManager.Instance.sceneRef` and then `StartCoroutine("LoadLoading")`. This loads the Loading scene through Addressables and releases the previous scene handle. `OnLevelFinishedLoading()` then finds `SceneRefs` (a per-scene component in `Assets/SceneRefs.cs`), the active player and the `EnemySpawner`, restores the save, and enables or disables portals depending on whether enemies remain.
- `Portal` saves the game and then triggers `LoadLoading` with its own `sceneRef`. `Portal.DestinationIdentifier` sets where the player spawns.
- Coroutines are often started by string name (`StartCoroutine("LoadLoading")`), so renaming those methods breaks things silently.

### Saving
- `SavingSystem` serialises a `Dictionary<string, object>` with `BinaryFormatter` to `Application.persistentDataPath/currentSaveName.sav`. Each `SaveableEntity` (unique ID) collects the state of every `ISaveable` component on its GameObject. Saved state must be `[Serializable]`; use `SerializableVector3` for positions.
- The save also stores `lastSceneBuildIndex` (actually the `LevelManager.sceneRef`) and `destination`, and Continue uses these to choose the level.
- `SavingWrapper` is the façade for Save/Load/Continue/Menu. Persistent managers are spawned once by `PersistentObjectsSpawner` (`Rambler.Core`). `Utils/PeristentObjectSpawner.cs` is the original GameDevTV version (a different class, so no conflict).

### AI: state machine
- `Control/Behaviours/StateMachine.cs` + `IState` (`Tick/OnEnter/OnExit`) are global classes with no namespace. Transitions are keyed by **state type**, plus "any" transitions that are checked first.
- Each enemy controller builds its states in `Awake`/`Start` using a local helper `At(to, from, condition)`, and calls `stateMachine.Tick()` in `Update`:
  - `Control/Timbertoes/TimbertoesCon.cs` with `T*` states (TPatrol, TAttack, TReload, TLaunch, TIdle; TDead is in Combat/)
  - `Control/Drone/DroneCon.cs` with `D*` states. `Drone` is a ScriptableObject that sets the drone type (suicide/ranged/health).
  - `Control/Misc Controllers/AIController.cs` uses the generic states in `Control/Behaviours/` (Patrol, Idle, Dead, ThrowGrenade, …)
- Field-of-view components (`FieldOfView`, `DroneFOV`, `TimbertoesFOV`) feed the transition predicates.

### Player, combat, movement
- `PlayerSelector` (ISaveable) manages the switchable player characters, lives and the UI buttons (interact, holster, reload, crouch, shields). It broadcasts changes through the static `UpdatePlayerObject` delegate.
- `PlayerController` reads **touch input** (`Input.GetTouch`, using the legacy Input Manager) and ignores touches over UI via `EventSystem`.
- `ActionScheduler` + `IAction` cancel the previous action (Mover, Fighter, TFighter, AIConversant) when a new one starts.
- Stats: `BaseStats` + `Progression` (ScriptableObject) + `IModifierProvider`. Health is in `Attributes/Health.cs`.

### Dialogue and quests
- `Dialogue` and `DialogueNode` are ScriptableObjects with a custom node editor (`Dialogue/Editor/`). Conditions use `IPredicateEvaluator`, which `QuestList` and `PlayerConversant` implement. `LevelManager.SetUpLevel` finds the HUD at the hard-coded path `/PlayerCore/HUD/Dialogue`.

### Monetisation and other packages
- Ads code is in `Ads/` (Google Mobile Ads, interstitial and rewarded). Photon, IAP and Matchmaker are installed but **not referenced by game code**.

## Source control

The project uses both git and Plastic SCM (`.plastic/`, `ignore.conf`). Don't commit `Library/`, `Temp/`, `Logs/`, `obj/` or the generated `.csproj`/`.sln` files. `user.keystore` is the Android signing keystore, so never modify or share it.

## Coding rules
- Namespace: BadStar.*
- No GetComponent/Find in Update; cache references
- Networking via Photon PUN2 only; use RPCs for X, properties for Y
- Don't edit Assets/Plugins or third-party folders
- Ask before modifying scenes or prefabs

## Backups

Run `./backup.sh "what changed"` from Git Bash in the project folder. It does three things:

1. **git: scripts only.** `.gitignore` tracks just `Assets/_Scripts` (code and data assets; models, audio and images inside it are left to Plastic), plus `.gitignore`, `backup.sh` and this file. Commit script work first. The script pushes every branch to the RANDY drive (`F:\BadStarBackup\git\BadStar.git`, remote `randy`) and the current branch to GitHub (remote `BadStar`, pushed with `http.sslBackend=schannel` because Git's own certificate list fails here).
2. **Plastic: everything else.** Models, scenes, prefabs, materials, `ProjectSettings` and `Packages` go to `BadStar@AnyColourYouLike@cloud` (CLI `D:\client\cm.exe`). `ignore.conf` keeps `Library`, `.git` and other tool folders out.
3. **RANDY (F:) mirrors.** `F:\BadStarBackup\unity` mirrors the project (without `Library`/`Temp`/`Logs`), and `F:\BadStarBackup\blender` mirrors the Blender sources in `D:\BadStar`. Plastic history stays in the cloud; F: holds the current files.
